# ODFlow v0.3 範本品質規格

## 目的

這份規格用來定義 v0.3 核心範本與核心輸出文件的最低品質標準，目標不是做複雜美編，而是讓文件看起來像真實可用的台灣校園社團文件。

## 正式文件格式規範

### 版面

1. 頁面尺寸以 A4 為主
2. 內容需保留合理頁邊距
3. 主要文件避免過度寬鬆的留白，讓內容看起來像正式行政文件

### 字體

1. 預設中文字體：標楷體
2. 若執行環境無法完全保證字型嵌入，仍應以標楷體為設計基準
3. 英數與符號需避免與中文字體衝突造成版面破碎

### 字級

1. 內文預設 12pt
2. 主標題應比內文大，建議 16pt 到 18pt
3. 次標題可落在 14pt 左右

### 標題

1. 文件標題置中
2. 標題需明確對應文件用途，例如「活動企劃書」「年度計畫」
3. 標題下方可放基本資料列，讓評審一眼看懂文件類型與對象

### 表格

1. 表格需有清楚框線
2. 欄位名稱簡潔且符合校園文件習慣
3. 欄寬與列高應優先服務可讀性，不追求花俏

## 空白範本與填表生成文件的差異

### 空白範本

1. 用途是讓使用者下載後自行填寫
2. 需保留真實欄位架構
3. 可包含示範欄位名稱與少量提示，但不應填入過多內容

### 填表生成文件

1. 用途是把使用者在系統中的表單資料輸出成可交付文件
2. 內容需帶入 `content_json` 中的值
3. 若某欄位為空，應有一致的留白策略，不要讓版面看起來像壞掉

## 真實範本 placeholder 策略

為了讓空白範本既可展示又不顯得過假，placeholder 建議遵守：

1. 只放真實欄位名稱，不要塞一大段假文案
2. 需要示範格式時，用簡短範例，例如「114/09/15」「活動地點」
3. 需要使用說明時，放在文件尾端或旁註，不要混進正式欄位主體
4. 同一種文件的 placeholder 規則要一致

## ODT / ODS 可能跑版的限制

這是 v0.3 必須承認並管理的限制：

1. ODT 在不同辦公軟體中的字距與行距可能略有差異
2. ODS 的欄寬、列高與自動換行在不同軟體中可能表現不同
3. PDF 匯出若不是來自同一排版引擎，最終視覺可能與 ODT / ODS 有細部差異

因此 v0.3 驗收應以「可開啟、可讀、格式穩定、接近正式校園文件」為主，不要求跨平台像素級一致。

## 如何從使用者提供的範本抽出欄位 schema

若未來要把真實社團文件範本納入系統，建議依以下步驟處理：

1. 先辨識文件目的與最終輸出型態，是空白範本還是填表生成文件
2. 把文件拆成固定區塊，例如標題、基本資料、表格區、備註區
3. 抽出真正需要結構化的欄位，避免把整份文件原樣硬塞成一個大文字欄
4. 判斷哪些欄位是單值，哪些是可重複陣列
5. 再設計對應的 `content_json` schema

## 如何把欄位 mapping 到 content_json

mapping 原則如下：

1. 文件標題類欄位映射到單一字串欄位
2. 人員、名冊、流程、預算等重複資料映射到陣列
3. 敘述段落映射到文字欄位
4. 若文件中同一區塊會重複出現，應整理成 repeatable section，而不是多個零散欄位
5. schema 命名要優先穩定與可讀，不要為了貼原始範本逐字命名

## 核心範本精修優先順序

v0.3 建議優先處理以下範本：

1. 會議紀錄 ODT
2. 會議通知 ODT
3. 會議議程 ODT
4. 活動企劃書 ODT
5. 活動成果報告 ODT
6. 活動檢討會紀錄 ODT
7. 年度計畫 ODT
8. 出席簽到表 ODS

其餘範本先以欄位整齊、命名一致、可下載開啟為主。

## 如何驗收產出的 ODT / ODS / PDF

### ODT

1. 可正常開啟
2. 標題置中且辨識明確
3. 內文字級一致
4. 表格線與欄位清楚
5. 空欄位不會造成版面崩壞

### ODS

1. 可正常開啟
2. 表頭明確
3. 至少有 3 到 5 列可直接填寫的示範列
4. 欄寬足夠閱讀
5. 列印或匯出時不會明顯失真

### PDF

1. 內容與來源文件對應
2. 標題、段落、表格可讀
3. 不出現明顯截斷或重疊
4. 可直接作為展示或評鑑上傳用途

## 驗收方式建議

1. 每個核心範本至少做一次實際生成與人工檢查
2. 同時檢查空白範本與帶入資料後的生成文件
3. 至少用一套本機辦公軟體與 PDF 檢視器驗證
4. 若使用者有提供真實校園範本，應拿來做比對而不是只看程式輸出
